# 04. 매치 예약

## 목적

"지금 상대가 없으면 시간을 약속한다." 계정 없이, 그날 하루 안에서 시각·매치 종류·계급 조건을 걸고
1~3명을 모집하는 경량 약속 기능.

## 도메인 규칙 (`reservation/domain.py`)

| 규칙 | 내용 |
|------|------|
| 시각 해석 | 호스트는 **시각만** 고른다. `21:00`은 서울 기준 다음에 오는 21:00이다. |
| 자정 롤오버 | 고른 시각이 이미 지났으면 다음 날로 넘긴다. 23:00에 고른 `00:30`은 익일 00:30 |
| 최소 리드타임 | 현재 시각 + **10분** 이후만 등록 가능 |
| 상한 | **다음 06:00 KST** 이전만 등록 가능. 그 뒤 시각은 400 |
| 예상 시간 | 30 / 60 / 120 / 180분 중 택1 (필드 범위 자체는 30~240) |
| 랭크 매치 | 계급 1개 이상 필수, 모집 인원은 **반드시 1명** |
| 플레이어 매치 | 계급 선택 불가 |
| 상관없음(`any`) | 계급·인원 제약 없음 |
| 계급 목록 | 중복 선택 불가, 최대 20개 |
| 메모 | 최대 140자 |
| 상태 전이 | `open` → 정원 충족 시 `matched`; 취소는 `cancelled`, 종료는 `ended` |

### 참가 가능 조건 (`ensure_joinable`)
`open` 상태 + 시작 전 + 정원 미충족.

### 수정 가능 조건 (`ensure_editable`)
`open`/`matched` + 시작 전 + **참가자 0명**.
참가자는 "그때의 조건"에 동의한 것이므로, 호스트가 시각이나 매치 종류를 바꾸면 동의한 적 없는 약속에 묶인다.
참가자가 생긴 뒤에는 수정 대신 취소 후 재등록한다.

### 참가 취소 조건
`open`/`matched` + 시작 전.

## 소유권 — 계정 없는 능력 토큰

`shared/security/credentials.py`의 `TokenCredentialManager`가 처리한다.

1. 예약 생성/참가 시 `secrets.token_urlsafe(32)`로 토큰을 발급한다.
2. 서버는 **SHA-256 해시만** 저장한다. 원본 토큰은 응답 1회로만 전달된다.
3. 이후 수정·취소는 `X-Reservation-Token` 헤더의 토큰을 해시해 비교한다.

FE는 `localStorage`에 `reservation-owner-{id}` / `reservation-participant-{id}`로 보관한다.
따라서 `isOwner(id)`는 "이 브라우저가 토큰을 갖고 있는가"이지 "같은 사람인가"가 아니다.

**알려진 한계**: 사이트 데이터를 지우거나 브라우저를 바꾸면 예약 삭제 권한을 영구히 잃는다.
복구 수단은 없다. 토큰 모델의 대가이지 버그가 아니다.

## API

| 메서드 | 경로 | 설명 | 인증 |
|--------|------|------|------|
| GET | `/reservations` | 지금부터 다음 06:00 KST까지의 `open`/`matched` 예약 목록 | 없음 |
| POST | `/reservations` | 등록 → `{ reservation, owner_token }` (201) | 없음 |
| GET | `/reservations/{id}` | 단건 조회 | 없음 |
| PATCH | `/reservations/{id}` | 부분 수정 | 호스트 토큰 |
| POST | `/reservations/{id}/participants` | 참가 → `{ reservation, participant_token }` (201) | 없음 |
| DELETE | `/reservations/{id}/participants/me` | 참가 취소 | 참가자 토큰 |
| DELETE | `/reservations/{id}` | 예약 취소 (204) | 호스트 토큰 |

## 조회 조건

### 하루의 경계는 자정이 아니라 새벽 6시

대전은 밤에 몰리고 자정을 넘겨 이어진다. 그래서 예약이 다루는 "하루"는 달력 날짜가 아니라
**다음 06:00 KST까지의 세션**이다. `domain.window_end(now)`가 그 경계를 계산한다 —
새벽 2시면 오늘 06:00(4시간 뒤), 저녁 9시면 내일 06:00(9시간 뒤).

이 경계는 조회와 등록 **양쪽에 같이 적용된다**. 볼 수 없는 구간에 예약이 만들어지지 않도록 하기 위해서다.

### 목록 — `GET /reservations`

파라미터가 없다. 창은 날짜가 아니라 **호출 시각**에 매달려 굴러간다.

| 조건 | 값 |
|------|-----|
| 시간 범위 | `start_at >= now` AND `start_at < window_end(now)` |
| 상태 | `open`, `matched`만 (`cancelled`·`ended` 제외) |
| 정렬 | `start_at` 오름차순, 같은 시각이면 `open`이 `matched`보다 앞 |
| `participant_count` | `cancelled_at IS NULL`인 참가자만 outer join으로 집계 |

하한이 `now`이므로 **이미 시작된 예약은 목록에서 빠진다.** 시작된 예약은 참가도 수정도 안 되는 죽은 항목이라,
목록은 "지금이라도 갈 수 있는 약속"만 담는다. 진행 중인 예약은 `GET /{id}`로만 볼 수 있다.

**조회는 만료 처리를 먼저 수행한다.** `_expire_finished()`가
`start_at + duration_minutes <= now` 인 live 예약을 `ended`로 바꾸고 그 참가자를 모두 해제한다.
이 갱신은 **요청한 날짜에 한정되지 않는다** — 어느 날짜의 예약이든 시간이 지나면 정리되어야 하기 때문이다.
행 단위가 아니라 두 개의 `UPDATE`문으로 처리하는 이유도 같다. 예약 탭이 10초마다 이 엔드포인트를 치므로
목록 비용이 테이블 크기를 따라 커지면 안 된다.

배치 잡이나 스케줄러는 없다. 만료는 **조회 시점의 lazy expiry**가 전부다.
따라서 아무도 조회하지 않는 동안에는 DB에 `open` 상태로 남아 있는 지난 예약이 존재할 수 있다.

### 알려진 트레이드오프 — 새벽의 좁은 창

00:00~06:00 사이에는 창이 최대 6시간까지 좁아진다. 새벽 1시에 접속한 사람은 그날 저녁 21:00 예약을
**등록할 수 없다**(400). 06:00을 지나 창이 다음 새벽까지 넓어지면 그때부터 가능해진다.
세션 단위로 창을 끊은 대가이며, 저녁 시간대(창이 9시간 이상)에는 드러나지 않는다.

### 단건 — `GET /reservations/{id}`

상태 필터도, 만료 처리도 하지 않는다. `cancelled`·`ended` 예약도 그대로 반환된다.
공유된 링크(`/reservation/:id`)로 들어온 사람이 "없는 예약"이 아니라 "끝난 예약"을 보게 하기 위한 동작이다.

### 클라이언트 측 조회 조건

- FE에는 **날짜 선택 UI가 없고, 날짜를 보내지도 않는다.** 창은 전적으로 서버가 정한다.
- 폴링 주기가 둘이다: 앱 전역 `useReservations()` 60초(내비 뱃지용), 예약 탭 자체 10초.
  탭이 열려 있는 동안에는 둘이 함께 돈다.
- 매치 종류 필터(전체 / 랭크매치 / 플레이어 매치)는 **클라이언트 필터**다. 서버에 종류 파라미터는 없다.
  `상관없음(any)` 예약은 어느 쪽 단일 필터에서도 남는다 — 호스트가 양쪽 다 받겠다고 한 것이므로.
- 목록은 시각별로 그룹핑한 뒤, 그룹 안에서 정원이 찬 항목을 뒤로 보낸다.
- 내비 뱃지 숫자(`countOpen`)는 `status === 'open' && participant_count < capacity`만 센다.
  이미 찬 예약을 눌러보라고 유도하지 않기 위해서다.

`PATCH`는 부분 패치가 **최종 상태 기준으로** 검증된다. 예를 들어 계급을 그대로 둔 채
매치 종류만 `player_match`로 바꾸는 요청은, 현재 값을 병합한 뒤 `ensure_conditions_valid`에 걸려 거부된다.

취소는 소프트 삭제(`status = 'cancelled'`)이며 참가자도 함께 해제한다.
목록 조회가 `open`/`matched`만 반환하므로, 취소된 예약은 다음 폴링에서 자연히 사라진다 — 클라이언트 측 제거 코드가 없다.

## 화면

- 경로 `/reservation`, 상세는 `/reservation/:id` (링크 공유 가능).
- 매치 종류 필터는 토글(전체 / 랭크매치 / 플레이어 매치). `any` 예약은 양쪽 필터에 모두 보인다.
- 등록 모달이 수정 폼을 겸한다 — 같은 필드, 같은 검증. 등록과 수정 사이에 규칙이 어긋날 수 없다.
- 참가자가 1명이라도 있으면 수정 버튼이 비활성화된다. 다만 **서버가 권위**다.
  모달을 연 사이에 참가자가 들어오면 400으로 막힌다.
- 라벨·KST 시각 포맷은 `reservationLabels.ts`에 둔다(개요 탭도 쓰고, 테스트가 API 모듈을 통째로 모킹하므로).
